# Patchwire Core Specification

`@patchwire/core` is the UI-agnostic library every client embeds (VS Code extension, CLI, and later Desktop). It consolidates the client-side logic that today is scattered across `cli/lib/client.ts`, the extension's `CliClient`, `resolveCli`, and `MutagenController`. Core is the authoritative **client-side mirror** of the agent (which remains the source of truth) and the only place client logic lives, so the clients stay thin and cannot diverge.

## Boundary decisions (locked)

- **Library-first, daemon-ready.** Core ships as an in-process TypeScript library embedded by the CLI and extension now. Its API is shaped so it can be promoted to a **local Core daemon** later without changing callers. The daemon is not built in this spec; daemon-*readiness* is.
- **Protocol-symmetric broker.** Core's client-facing API reuses the agent Protocol v2 envelope and event taxonomy, plus client-only command verbs and event families. Core speaks Protocol v2 to clients and to the agent — it is a local broker.

## Scope

In scope: the Core public API (typed command domains, snapshots, event subscription), the state Core owns, the `HostPlatform` adapter, projection *application*, sync orchestration and conflict handling, the durable offline queue, and the daemon-promotion invariants.

Out of scope (delegated): the projection *rule language* and policy engine (Projection & Policy spec — Core consumes their compiled output); UI/rendering (each client); the Linux/Windows server implementations (Agent spec's S2/S3); the daemon implementation itself (a later spec, unblocked by the invariants here).

## Non-goals

Core does not own UI, does not define projection rules, and does not introduce the daemon, gRPC, or any new transport. It stays on the Protocol v2 surface (HTTP commands + duplex WebSocket) defined by the Agent spec.

---

## Pillar 1 — Responsibilities & boundary

Core owns everything between the client UI and the agent: connection lifecycle, the Protocol v2 client (HTTP commands + duplex WS), the **identity context**, the session registry, sync orchestration, the policy/projection cache, the local cache + projection materialization, conflict tracking, the durable offline queue, and the `HostPlatform` adapter. Clients contribute only surface: they render Core state and emit user intent. They hold no authoritative state and never talk to the agent directly.

## Pillar 2 — Client API

Two entry points, both fully serializable so they survive promotion to an IPC/daemon boundary unchanged:

```ts
core.send(command: CoreCommand): Promise<CoreResponse>;   // request/response
core.subscribe(handler: (event: CoreEvent) => void): Unsubscribe;  // server-push
```

### Typed command domains (revision 1)

Commands are **not** a flat `(string, any)` pair. They are a discriminated union organized into typed **domains**, each with typed payloads and responses, mirroring the event families:

```ts
type CoreCommand =
  | { domain: 'connection'; verb: 'connect' | 'disconnect' | 'snapshot'; payload: ConnectionPayload }
  | { domain: 'provision';  verb: 'start' | 'snapshot';                  payload: ProvisionPayload }
  | { domain: 'session';    verb: 'create' | 'open' | 'cancel' | 'snapshot'; payload: SessionPayload }
  | { domain: 'chat';       verb: 'send' | 'cancel';                     payload: ChatPayload }
  | { domain: 'ask';        verb: 'run';                                 payload: AskPayload }
  | { domain: 'sync';       verb: 'pause' | 'resume' | 'snapshot';       payload: SyncPayload }
  | { domain: 'conflict';   verb: 'list' | 'resolve';                    payload: ConflictPayload }
  | { domain: 'branch';     verb: 'integrate';                           payload: BranchPayload }
  | { domain: 'policy';     verb: 'snapshot';                            payload: PolicyPayload };
```

Domains divide cleanly into **agent-passthrough** (`provision`, `session.create`, `chat`, `ask` — Core forwards them to the agent, stamping the envelope) and **client-only** (`connection`, `session.open`, `sync`, `conflict`, `branch`, `policy.snapshot` — Core handles them locally; they never reach the agent verbatim).

### Snapshot / state query (revision 2)

Events deliver deltas, but a client that just attached (or re-attached to a future daemon) needs current full state without replaying history. Every stateful domain supports a **`snapshot` verb**, and Core exposes a top-level aggregate:

```ts
core.snapshot(): Promise<CoreSnapshot>;

interface CoreSnapshot {
  connection: ConnectionState;
  sessions: SessionRecord[];
  sync: SyncState;
  conflicts: Conflict[];
  policyVersion: string;
  projectionVersion: string;
  capabilities: ServerCapabilities;
  queueDepth: number;        // pending offline-intent items
}
```

The contract for clients: **snapshot once on attach, then apply `subscribe` deltas.** This is mandatory rather than optional because the daemon model has clients attaching to an already-running Core mid-stream.

### Identity owned by Core (revision 7)

Clients **never construct or set identity.** Core holds the authenticated `IdentityContext` for the connection and injects it into every outbound envelope:

```ts
interface IdentityContext { issuer: string; subject: string; type: 'workspace' | 'user' | 'service'; }
```

Core obtains the context at `connection.connect` (from the workspace credential), keeps it for the connection's life, and stamps `identity` (and a fresh `requestId`) onto every command it forwards. This centralizes the identity claim the Agent spec locked, prevents a client from forging or diverging identity, and means the move to per-user identity later is a Core-internal change invisible to clients.

## Pillar 3 — State Core owns

### Connection state machine + reason codes (revision 3)

```ts
type ConnectionState =
  | { state: 'disconnected' }
  | { state: 'connecting' }
  | { state: 'online' }
  | { state: 'degraded'; reason: DegradeReason }
  | { state: 'offline';  reason: OfflineReason };

type OfflineReason  = 'network-lost' | 'agent-unreachable' | 'auth-expired' | 'tailnet-down' | 'user-paused';
type DegradeReason  = 'ws-dropped-http-ok' | 'high-latency' | 'partial-capability';
```

Transitions are **machine-readable**, not just a label: `connection.*` events carry the reason so clients render meaningful UI ("offline — Tailscale down" vs "offline — auth expired, re-login") and Core picks the right retry behavior (reconnect WS vs re-auth vs wait for network).

### Session registry

Mirrors the agent's `SessionState` (`Created → Preparing → Running → WaitingForReview → Completed/Cancelled/Failed`). Updated by `session.*` events; queried via `session.snapshot`.

### Conflicts with stable IDs (revision 4)

```ts
interface Conflict {
  id: string;            // stable conflictId — referenced by events and commands
  path: string;
  localRev: string; remoteRev: string;
  projectionVersion: string;   // the projection in force when detected
  state: 'open' | 'resolved';
  resolution?: 'take-local' | 'take-remote' | 'merged';
}
```

`conflict.detected` / `conflict.resolved` events and the `conflict.resolve` command all reference a `conflictId`, so a long-lived conflict is addressed unambiguously across reconnects and across clients.

### Policy / projection cache with versioning (revision 5)

Core caches the compiled policy and projection, each carrying a **monotonic version** (or content hash). `policy.updated {version}` and `projection.updated {version}` advance it. Crucially, **commands that depend on the projection carry the `projectionVersion` they assume**; the agent rejects a mismatch with a `stale-projection` error, and Core refreshes the projection and replays. This is a security property, not just hygiene: acting on a stale projection could write to a path that is now hidden or expose one that is now redacted. Core never operates against a projection version it cannot confirm current.

## Pillar 4 — `HostPlatform` adapter

Core's only client-side OS seam:

```ts
interface HostPlatform {
  resolveMutagen(): Promise<string>;       // PATH → bundled → checksum-verified download to ~/.patchwire/bin
  captureClipboardImage(): Promise<string | null>; // mac pngpaste/osascript · win PowerShell · linux xclip/wl-paste
  discoverTool(name: string): Promise<string | null>; // e.g. Tailscale (not on PATH on Windows)
  normalizePatch(patch: string): string;   // CRLF-safe round-tripping
}
```

This adapter is where **migration phase S0 (cross-platform client to a Mac server)** lands — Mutagen-everywhere and the Windows/Linux papercut fixes are implemented here, behind one interface.

## Pillar 5 — Projection application (boundary with the Projection spec)

Core **applies** projections; it does **not** define them. It receives a *compiled* projection from the agent (versioned, per Pillar 3), materializes the authoritative remote view into the local cache, **enforces projected paths as read-only and excludes them from write-back**, and routes local edits back as pending intent. The rule language, redaction transforms, and policy engine live in the Projection & Policy spec; Core consumes their compiled, versioned output and is the enforcement point on the client side.

---

## Pillar 6 — Sync orchestration & conflict

Core drives Mutagen through `HostPlatform.resolveMutagen()`, emits `sync.*` events, and on divergence applies the parent doc's conflict strategy: clean changes propagate, true conflicts are quarantined and surfaced as **reviewable diffs** (`conflict.detected` with a `conflictId`), and projected paths are never written back. Resolution is an explicit `conflict.resolve` command — never a silent winner.

---

## Pillar 7 — Offline: durable deferred-intent queue (revision 6)

The offline queue is **persisted to disk**, not held in memory, so closing or crashing a client never loses queued intent:

- Stored append-only at `~/.patchwire/queue/<workspaceId>.jsonl`. Each item: `{ id, requestId, command, enqueuedAt, projectionVersion }`.
- While offline, the cached projection stays editable; uncached paths are read-only; intent enqueues instead of failing.
- On reconnect, Core **replays in enqueue order**, idempotent via `requestId` (the agent dedups), and **revalidates `projectionVersion`** per item — an item computed against a now-stale projection is dropped into the conflict path rather than applied blindly.
- `connection.*` events tell clients which mode they are in; `queueDepth` in the snapshot shows backlog.

Offline never promotes the local copy to a source of truth; it only defers the moment intent reaches the truth.

## Pillar 8 — Daemon-promotion invariants & runtime capability changes

### Invariants that keep Core IPC-shaped

Promoting Core to a daemon must change nothing observable. The spec names the invariants that guarantee it:

1. **All** client interaction goes through `send` / `subscribe` / `snapshot`. No client ever reaches into Core internals.
2. **No shared mutable objects** cross the boundary; every payload and event is serializable (structured-clone / JSON safe).
3. State is reconstructable from `snapshot` + event deltas — a client attaching mid-stream needs nothing else.
4. The durable queue and local cache are addressed by path under `~/.patchwire`, not by in-process handles.

### Logical singleton — clarified (revision 9)

"Singleton" means **one logical Core authority per (machine, OS user)** — not one per client process. Today, in library mode, a client process embeds Core in-process; if more than one embedder runs concurrently, they coordinate through **on-disk locks** under `~/.patchwire` for the shared durable queue and local cache, so two in-process Cores cannot corrupt shared state. The design forbids any in-memory-only state that would behave differently once N embedders collapse into the single daemon process. Post-daemon, there is literally one Core; pre-daemon, the embedders behave *as if* there is.

### Runtime capability changes (revision 8)

Server capabilities can change at runtime — an elevation during provisioning enables egress, or a re-detection changes a descriptor. Core surfaces this with a `capability.updated { capabilities }` event so clients react live (e.g. flip an "egress: enforced" badge) without reconnecting. The capabilities also appear in `CoreSnapshot` for newly-attached clients.

## Strangler reuse map

| Existing code | v2 role in Core |
|---|---|
| `cli/lib/client.ts` (`AgentClient`, `streamPostNdjson`, `parseAskStream`) | Core's Protocol v2 client (extend HTTP → HTTP + WS) |
| extension `cli/CliClient.ts`, `resolveCli.ts` | folded into Core; the extension stops spawning the CLI and embeds Core |
| extension `sync/MutagenController.ts` | folded into Core sync orchestration + `HostPlatform.resolveMutagen` |
| extension clipboard / `lib/patch.ts`, Tailscale lookups | `HostPlatform` methods |
| `cli` commands | become thin Core embedders |

## Mapping to migration phases

- **S0 (cross-platform client → Mac server)** is implemented inside Core's `HostPlatform` (Mutagen-everywhere + papercut fixes). This is the first shippable slice and depends on no server-side change.
- The **client half of S1** (Protocol v2 client, session/conflict/connection state, offline queue) is Core; the server half is the Agent spec.

## Open questions (tracked, not blocking)

- WebSocket reconnect/event-replay window vs. snapshot-on-reconnect (coordinate with the Agent spec's same open item).
- Local-cache eviction policy and maximum offline footprint.
- Multi-embedder lock contention details (acceptable until the daemon lands; the daemon removes the question).
- Where `branch.integrate` UX lives across Core vs. client (Core exposes the verb; rendering is the client's).
